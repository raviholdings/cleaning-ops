# 이미지 풀 조합 아키텍처 — 세트×장면 랜덤 조합 권장안

2026-08-20 확정. 새 프로젝트(세트 10 × 장면 10 = 100장, 페이지마다 장면 1~10을
순서대로 1장씩)에 쓸 방식. 청소(공간 10 × 50장)·이사(유형 25 × 20장)에서
실증된 패턴을 그대로 잇는다.

## 결론 요약

| 결정 | 권장 | 기각한 대안 |
|---|---|---|
| 폴더링 | **단일 평면 폴더 + 자기서술 파일명** `01_03.png` (장면01, 세트03) | 장면별 폴더 `01/ ~ 10/` |
| 추출 | **페이지 ID 기반 결정적 해시, 위치별 독립 추출** (조합 10^10) | seeded 셔플 순열 (조합 10!) |
| 저장 | 원본 100장만 CDN(R2)에 1회 업로드, HTML 은 URL 참조 | 페이지별 이미지 복제 |

## 1. 폴더링 — 단일 평면 폴더

```
img-v1/01_01.png … img-v1/10_10.png     ← {장면:2자리}_{세트:2자리}
```

- R2/S3 는 어차피 폴더가 없다(키 문자열). 평면이면 코드 원천이 배열 하나로
  끝나고, 업로드 후 전수 200 확인 루프도 한 줄이다.
- 파일명이 의미(장면·세트)를 품어야 코드-실파일 불일치를 눈으로 잡는다.
- **목록은 손으로 치지 말고 실제 파일에서 스크립트로 생성한다.** 이사 때
  손으로 적다가 유형 3개가 빠져 이후 번호가 전부 밀린 사고가 있었다
  (399번이 엉뚱한 유형을 가리킴 — scripts/lib/moving-page-data.mjs GALLERY 주석).
- 버전 폴더(`img-v1/`)로 감싼다. immutable 캐시(1년) 전제라 **내용이 바뀌면
  같은 경로에 덮어쓰지 말고 v2 로 올린다** (docs 의 R2 규칙, 청소 v3 사건).

## 1-1. 이미지에 묶을 공통점이 없을 때

파일명의 앞자리는 스타일·세트 같은 의미를 묶는 게 아니라 **"페이지의 몇 번째
자리 후보인가"** 만 표시한다. 같은 자리의 후보 10장이 서로 완전히 달라도
무방하다 — 공통점은 애초에 쓰지 않는다.

자리(장면 순서) 개념조차 없이 전부 호환이면 더 단순하다:

```
img-v1/001.png ~ img-v1/100.png      ← 일련번호만
```

페이지마다 100장 중 중복 없이 10장을 시드 셔플로 뽑는다. 조합은
100P10 ≈ 6×10^19 로 자리 고정 방식(10^10)보다 오히려 크다.

```js
function pickTen(pageId) {          // 시드 셔플 앞 10개 — 중복 없음 보장
  let s = hash(`myproj-v1|${pageId}`);
  const rand = () => (s = Math.imul(s ^ (s >>> 15), 0x2545F491), (s >>> 0) / 4294967296);
  const pool = Array.from({ length: 100 }, (_, i) => i + 1);
  for (let i = 0; i < 10; i++) {
    const j = i + Math.floor(rand() * (100 - i));
    [pool[i], pool[j]] = [pool[j], pool[i]];
  }
  return pool.slice(0, 10).map((n) => `${String(n).padStart(3, '0')}.png`);
}
```

"몇 장씩 뽑을지"만 다르지, 청소·이사의 pickImages 와 같은 계열이다.

## 2. 추출 — 결정적 해시, 위치별 독립

Math.random 금지. **같은 페이지는 언제 다시 생성해도 같은 조합**이 나와야
재굽기·부분 재배포·디프 검증이 성립한다 (청소·이사 렌더러가 전부 이 성질에
기댄다).

```js
function hash(str) {            // FNV-1a
  let h = 0x811c9dc5;
  for (let i = 0; i < str.length; i++) { h ^= str.charCodeAt(i); h = Math.imul(h, 0x01000193); }
  return h >>> 0;
}
const SETS = 10, SCENES = 10;
function pickImages(pageId) {
  const out = [];
  for (let scene = 1; scene <= SCENES; scene++) {
    const set = hash(`myproj-v1|${pageId}|scene${scene}`) % SETS + 1;
    out.push(`${String(scene).padStart(2, '0')}_${String(set).padStart(2, '0')}.png`);
  }
  return out;
}
```

- 시드에 **프로젝트 솔트+버전**(`myproj-v1|`)을 넣는다. 조합을 통째로 다시
  섞고 싶으면 솔트만 올리면 된다.
- 파일 중복은 구조상 불가능하다 — 위치마다 장면 번호가 달라서 같은 파일이
  한 페이지에 두 번 나올 수 없다.
- 독립 추출을 고른 이유: 조합 10^10. 50만 페이지 기준 완전 동일 조합 쌍
  기대값 ~12쌍(생일 문제)으로 유사문서 관점 무시 가능.
- 대안(기각): 페이지 시드로 세트 배열을 셔플해 위치 i 에 perm[i] 세트를
  쓰면 한 페이지 안에서 세트 반복이 없어 색감 통일이 안 드러나는 장점이
  있지만, 조합이 10!(363만)로 줄어든다. 같은 세트 반복이 실제로 눈에
  거슬리면 그때 전환한다 — 솔트 버전만 올리면 되므로 전환 비용은 재굽기뿐.

## 3. 부풀려진 주장 교정 (실측 기준)

떠도는 설명엔 과장이 섞여 있다. 이 레포 실측으로 바로잡는다.

1. "저장 20TB → 200MB": 결론은 맞지만 비교가 허수아비다. 실질 이득은
   "페이지 HTML 이 장당 ~8.7KB(gzip)" 쪽이다.
2. "CDN 100% 히트 영구 보관": 보장 아니다. 실측에서 R2 커스텀 도메인이
   `cf-cache-status: DYNAMIC`(엣지 캐시 안 됨)로 나왔다. R2 라 이그레스
   비용은 0이지만, 엣지 캐시를 원하면 **Cache Rule 을 명시적으로 걸어야
   한다** (미적용 상태, 개선 후보).
3. "1만 사이트 빌드 1~2분": 한 자릿수 이상 과장. 실측 — 이사 1만 사이트
   굽기 8~14분, 병목은 빌드가 아니라 **HTML 전송(4.2GB ≈ 1.5시간)**.
4. "진단 점수 만점·색인 누락 없음": 근거 없는 보장. 색인은 수집요청·
   사이트맵·문서 품질 싸움이다. 청소 색인 94% 는 수집요청 그라인드로 만든
   숫자이지 이미지 속도가 만든 게 아니다.

SEO 는 이미지 조합보다 **alt 텍스트·본문이 페이지마다 달라지는 것**이 더
중요하다. 이미지 파일 자체는 전 페이지가 같은 CDN URL 을 공유해도 문제
없었다 (청소·이사 실증).
