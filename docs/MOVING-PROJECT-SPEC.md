## 주소 체계가 왜 별도 작업인가

청소는 `/1.html` ~ `/131.html` 이다. 이사는 `/이사/{지역}-{키워드}` 로 간다.
바뀌는 곳이 한둘이 아니다.

| | 청소 | 이사 |
|---|---|---|
| 파일명 | `1.html.gz` | 한글 경로를 어떻게 파일로 떨굴지 |
| nginx | `rewrite ^/([0-9]+)$ /$1.html` | `/이사/...` 매핑 |
| 사이트맵 | `/1` ~ `/131` | 새 주소 |
| 수집요청 | `page_count` 로 URL 생성 | 지역+키워드로 생성 |
| 색인 조사 | URL 패턴 판별 | 새 패턴 |
| 카탈로그 | `(사이트, 번호) → (지역, 키워드)` | 역방향도 필요 |

**청소 131만 장은 주소를 바꾸지 않는다.** 색인이 94% 붙어 있어서 주소를
바꾸면 전부 날아간다. 새 체계는 이사·철거에만 적용한다.

## 페이지 증설 설계 — 블록 append (2026-08-21 확정)

운영자 방침: 사이트당 장수를 제한 없이 늘릴 수 있어야 한다.

현재 카탈로그는 사이트당 폭 100(SLOT_STRIDE)을 예약해 "기존 페이지 불변"을
보장한다. 따라서 **100장까지는 코드 변경 없이** 늘릴 수 있다 (재고
72,938×20=1,458,760 > 슬롯 100만이라 중복도 없다).

100장을 넘길 때는 스트라이드를 바꾸지 말 것 — 전 페이지 내용이 리매핑된다.
대신 **블록 append**:

    블록 1: rid 1~100   = 현재 카탈로그 (지역 × 메인 20) — 영원히 동결
    블록 2: rid 101~N   = 지역 × 새 키워드 세트 A (서브 승격/신규 발굴)
    블록 3: ...

- 블록마다 키워드 세트를 배타적으로 가지므로 블록 간 조합 중복이 구조적으로 0
- 새 블록 추가는 기존 블록의 슬롯·시드를 건드리지 않는다 (append-only)
- catalogEntry 에 "rid → 블록 → 그 블록의 (키워드셋, 시드)" 분기 한 겹만 추가
- 새 메인 키워드 1개 = +72,938 조합 = 사이트당 +7.3장.
  서브 77개 전부 승격 시 산술상 사이트당 ~700장.

코드 밖 한계: EC2 디스크(100만 장 ≈ 8.4GB, 700만 장 ≈ 59GB → 증설 필요),
수집요청 할당량(사이트당 50건/일), DB 결과 테이블 성장.
