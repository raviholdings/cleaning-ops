> 작성일: 2026-08-27  
> 분석 대상: [https://cloggedpipe.co.kr/](https://cloggedpipe.co.kr/)  
> 적용 대상: `cleaning-ops` 배관 정적 사이트 시스템  
> 문서 목적: 경쟁 사이트의 정보구조·지역 SEO·콘텐츠·전환 구조를 분석하고, 현재 배관 프로젝트에 구현 가능한 제품·개발 사양으로 변환한다.

## 0. 문서 요약

분석 대상 사이트는 다음 공식을 사용한다.

```text
서비스 허브 페이지
+ 시·구 단위 장문 랜딩페이지
+ 동·읍·면 × 서비스 키워드 조합
+ 현장 사례형 본문
+ 강한 내부링크 앵커텍스트
+ 전화 중심 CTA
+ FAQ·지역 서비스 구조화 데이터
```

벤치마킹 시 그대로 가져올 요소:

- 지역과 증상, 작업법, 비용 의도를 한 문서 안에서 연결하는 정보구조
- 예방 → 원인 → 진단 → 작업 → 비용 → 상담 순서의 콘텐츠 흐름
- 서비스 허브와 지역 랜딩페이지 사이의 내부링크
- H1, 메타 설명, 소제목, 이미지 대체 텍스트의 일관된 주제 신호
- 현장 유형별 설명과 FAQ
- 전화 CTA의 반복 노출

그대로 복제하지 않을 요소:

- 무작위 영문 URL
- 하단의 대량 키워드 나열
- 지역명만 치환한 유사 문서
- 실제 근거가 없는 전국·30분 출동 표현
- 지역 페이지 안에 무관한 다른 지역명을 섞는 방식
- 홈페이지 H1 누락과 구조화 데이터 타입 혼용

우리 구현 방향은 **대량 페이지를 유지하되, 페이지마다 명확한 검색 의도와 사용자 효용을 갖는 결정적 정적 생성 시스템**이다.

실제 예시:

```text
강남구싱크대막힘 하수구막힘 역류 고압세척

오산 싱크대막힘 하수구막힘 비용 얼마
용인 기흥구 싱크대막힘 하수구막힘 상가 뚫음
```

### 2.3 우리 프로젝트의 키워드 계층

현행 `data/keywords/piping-keywords.json`을 기준으로 세 단계로 관리한다.

```text
업종
├─ 막힘
│  ├─ 메인: 하수구막힘, 싱크대막힘, 배관청소, 고압세척 등 38개
│  └─ 서브: 비용, 역류, 내시경, 아파트, 상가, 공용관 등
├─ 수전
│  ├─ 메인: 수전교체, 수전설치, 수도꼭지교체 등 11개
│  └─ 서브: 주방, 욕실, 세면대, 가격, 셀프교체 등
└─ 누수
   ├─ 메인: 누수탐지, 누수점검, 천장누수 등 21개
   └─ 서브: 아파트, 빌라, 상가, 비용, 보험, 배관 등
```

개발 규칙:

- 페이지 하나는 메인 키워드 하나를 대표한다.
- 서브 키워드는 제목에 최대 1개, 본문에 2~4개만 자연스럽게 사용한다.
- 서로 다른 문제군을 무작정 한 제목에 넣지 않는다.
- `막힘`, `수전`, `누수` 문서 템플릿을 분리한다.
- 비용 키워드는 비용 설명 섹션이 있는 페이지에서만 사용한다.
- 업체·긴급출동 키워드는 실제 제공 범위와 운영 시간이 확인된 경우에만 사용한다.

### 2.4 검색 의도 매핑

| 의도 코드 | 사용자 질문 | 권장 페이지 유형 | 필수 섹션 |
|---|---|---|---|
| `urgent` | 지금 막혔는데 누가 오나 | 지역 서비스 페이지 | 증상, 출동 범위, 전화 CTA |
| `cause` | 왜 역류하거나 냄새가 나나 | 원인 설명형 | 원인, 자가 점검, 전문가 필요 조건 |

| `case` | 비슷한 현장을 해결했나 | 현장 사례형 | 현장 조건, 진단, 작업, 결과 |
| `provider` | 근처 업체를 찾는다 | 지역 업체형 | 서비스 지역, 대응 가능 작업, 문의 |

## 3. 지역 SEO 구조

### 3.1 경쟁 사이트의 지역 계층

경쟁 사이트는 시·구 단위 페이지에서 하위 동·읍·면 키워드까지 포괄한다.

```text
광역 지역
→ 시·군·구 대표 페이지
→ 페이지 본문에 대표 동 포함
→ 하단에서 동·읍·면 × 서비스 조합 나열
→ 인접 시·구 페이지로 내부링크
```

강남구 페이지 예시:

```text
강남구 대표 문서
├─ 역삼동
├─ 개포동
├─ 청담동
├─ 삼성동
├─ 대치동
├─ 신사동
├─ 논현동
├─ 압구정동
├─ 세곡동
├─ 자곡동
├─ 율현동
├─ 일원동
├─ 수서동
└─ 도곡동
```

각 하위 지역을 다시 `하수구막힘`, `싱크대막힘`, `역류`, `고압세척`과 조합한다.

### 3.3 우리 시스템의 지역 데이터 원칙

현행 지역 풀은 `data/locations/rollout-locations.json`의 72,938개이며, 기존 결정적 배정 때문에 목록을 수정하면 안 된다.

필수 필드 모델:

```ts
type Location = {
  id: string;
  sido: string;
  sigungu: string;
  eupmyeondong: string;
  displayName: string;
  titleName: string;
  parentDisplayName: string;
  nearbyLocationIds: string[];
  locationType: 'gu' | 'si' | 'gun' | 'dong' | 'eup' | 'myeon';
};
```

기존 파일을 바꾸지 않고 필요한 파생값은 런타임 또는 별도 인덱스 파일에서 계산한다.

### 3.4 지역명 표기 규칙

| 위치 | 표기 방식 | 예시 |
|---|---|---|
| Title | 대표 지역 1회 | `강남구 하수구막힘 고압세척 비용과 작업 과정` |
| H1 | 대표 지역 + 메인 서비스 | `강남구 하수구막힘 배관 고압세척` |
| 리드문 | 시·구 + 동 자연어 | `강남구 역삼동·논현동 등에서...` |
| 사례 | 실제/가상 시나리오 지역 1곳 | `강남구 상가 주방 배관 사례` |
| 서비스 지역 | 하위 지역 목록 | `역삼동, 논현동, 대치동...` |
| 내부링크 | 인접 지역 + 서비스 | `서초구 하수구막힘 안내` |
| 이미지 alt | 장면 설명 + 지역은 필요한 경우만 | `강남구 상가 배관 내시경 점검` |

금지:

- 한 문장마다 지역명을 반복하지 않는다.
- 동 이름과 키워드를 쉼표 없이 수백 개 나열하지 않는다.
- 제목의 지역과 무관한 지역명을 본문 결론에 넣지 않는다.
- 출동하지 않는 지역을 `areaServed`에 넣지 않는다.

## 4. 페이지 유형과 URL 설계

### 4.1 권장 논리 IA

```text
/
├─ /service/{service}/
│  ├─ /service/drain-clog/
│  ├─ /service/sink-clog/
│  ├─ /service/high-pressure-cleaning/
│  ├─ /service/pipe-camera/
│  ├─ /service/faucet-replacement/
│  └─ /service/leak-detection/
├─ /area/{sido}/{sigungu}/
├─ /case/{case-id}/
├─ /guide/{topic}/
├─ /price/
├─ /faq/
└─ /contact/
```

현재 배포 시스템의 확정 URL은 `/piping/{페이지번호}`이므로 당장 변경하지 않는다. 대신 페이지 HTML 안에서 `breadcrumb`, canonical, 제목 및 내부링크를 통해 논리 계층을 표현한다.

향후 URL 개편 시에는 301 리다이렉트·사이트맵·수집요청 dedup 영향을 별도 검토해야 한다.

### 4.2 페이지 타입

| 타입 | 목적 | 생성 단위 | 대표 CTA |
|---|---|---|---|
| 홈 | 업종과 신뢰 설명 | 호스트당 1 | 전화·상담 |
| 서비스 허브 | 서비스군 설명 | 서비스군당 1 | 관련 지역 찾기 |
| 지역 서비스 | 지역+메인 키워드 | 현행 대량 페이지 | 전화·접수 |
| 비용 가이드 | 비용 결정 요인 | 메인 서비스별 | 견적 접수 |
| 현장 사례 | 경험·결과 증명 | 사례 데이터별 | 유사 현장 상담 |
| FAQ | 롱테일 질문 대응 | 질문군별 | 추가 문의 |

## 5. 지역 랜딩페이지 상세 템플릿

### 5.1 전체 순서

```text
1. 상단 긴급 안내
2. 헤더·전화 버튼
3. Breadcrumb
4. H1 + 지역·서비스 요약
5. 핵심 CTA
6. 증상 체크리스트
7. 원인 설명
8. 현장 유형별 진단
9. 작업 과정
10. 장비와 선택 기준
11. 비용 결정 요인
12. 작업 전후 또는 사례
13. 서비스 가능 하위 지역
14. FAQ
15. 인접 지역·관련 서비스
16. 상담 폼
17. 사업자·고지 정보
18. 모바일 고정 전화 CTA
```

### 5.2 섹션별 요구사항

#### A. 히어로

- H1은 페이지당 정확히 1개다.
- 대표 지역과 메인 키워드는 한 번씩 포함한다.
- 보조문구에는 증상 또는 작업법 하나를 넣는다.
- CTA는 `전화하기`, `상담 접수` 두 가지다.
- 확인되지 않은 `30분 도착`, `무조건 해결`, `최저가` 표현은 금지한다.

예시:

```text
H1: 강남구 하수구막힘 배관 고압세척
설명: 상가·아파트 배관의 역류 원인을 점검하고 현장에 맞는 작업 방법을 안내합니다.
CTA: 전화 상담 / 현장 정보 남기기
```

#### B. 증상 체크

- 사용자 관찰 기준 4~6개
- 증상에 따라 예상 배관 범위를 안내
- 자가 해결이 위험한 조건을 표시

#### C. 원인

- 서비스별 원인 풀에서 3~5개 선택
- 지역명은 섹션 첫 문단에만 자연스럽게 사용
- 원인마다 권장 진단법을 연결

#### D. 작업 과정

권장 5단계:

```text
현장 확인 → 배관 구조 파악 → 내시경/관로 진단 → 적합 장비 작업 → 통수·재점검
```

#### E. 비용

정찰 가격을 제공할 수 없으면 가격 숫자를 억지로 넣지 않는다. 대신 다음 결정 요인을 설명한다.

- 배관 길이와 구경
- 막힘·오염 정도
- 단독관/공용관 여부
- 작업 지점 접근성
- 투입 인원과 장비
- 야간·휴일 여부
- 추가 보수공사 필요 여부

#### F. 하위 지역

키워드 표가 아니라 사용자용 서비스 범위로 표현한다.

```text
강남구 서비스 가능 지역
역삼동 · 논현동 · 삼성동 · 대치동 · 청담동 · 개포동 · 도곡동 · 수서동 등
```

지역명마다 모든 키워드를 반복하지 않는다.

#### G. FAQ

- 페이지당 3~5개
- 본문에 실제로 보이는 질문만 JSON-LD에 포함
- 비용, 작업 시간, 재발, 고압세척 필요 조건, AS 범위를 우선

#### H. 관련 링크

- 같은 지역의 관련 서비스 2개
- 같은 서비스의 인접 지역 2~3개
- 관련 비용/가이드 1개
- 링크 앵커는 자연스러운 문장으로 작성

```ts
type PipingLandingPage = {
```

### 6.2 문구 풀 모델

```ts
type ContentPool = {
  leads: Record<string, string[]>;
  symptoms: Record<string, string[]>;
  causes: Record<string, string[]>;
  diagnostics: Record<string, string[]>;
  processes: Record<string, string[]>;

  cautions: Record<string, string[]>;
  ctas: Record<string, string[]>;
```

### 6.3 결정적 생성 규칙

현재 시스템의 `(siteIndex, pageId)` 결정적 생성을 유지한다.

- 동일 입력은 항상 동일 HTML을 생성한다.
- 지역 풀의 순서와 개수는 변경하지 않는다.
- 문구 선택은 `variantSeed` 기반으로 한다.
- 페이지 증설 시 기존 페이지의 지역·키워드·문구가 바뀌지 않아야 한다.
- 동일 호스트 내에서 H1과 메타 설명의 완전 중복을 허용하지 않는다.
- 인접 링크 선택도 seed 기반으로 고정한다.

### 6.4 콘텐츠 다양화 축

페이지마다 최소 5개 축이 달라져야 한다.

1. 검색 의도
2. 건물 유형
3. 대표 증상
4. 원인 조합
5. 작업 과정 강조점
6. 비용 설명 방식
7. FAQ 조합
8. 이미지 조합
9. CTA 문구
10. 관련 링크 조합

지역명만 바뀌고 문장이 동일한 페이지는 생성 실패로 처리하는 검사를 둔다.

## 7. 제목·메타·헤딩 생성 사양

### 7.1 Title

권장 길이: 한글 기준 약 25~40자.

템플릿:

```text
{지역} {메인키워드} {서브키워드} | {핵심효익}
{지역} {메인키워드}, {증상} 원인과 작업 방법
{지역} {메인키워드} 비용을 정하는 {숫자}가지 기준
{지역} {건물유형} {메인키워드} 현장 점검 안내
```

금지:

- 핵심어 4개 이상 연속 나열
- 같은 단어 2회 이상 반복
- 페이지 내용에 없는 `비용`, `가격`, `후기` 사용
- 모든 페이지에 동일한 접미사 사용

### 7.2 Meta description

- 80~130자 권장
- 지역, 메인 서비스, 대표 증상, 해결 방식, CTA를 자연어로 작성
- 동 이름 나열은 최대 3개

예시:

```text
강남구 상가와 아파트의 하수구막힘·역류 원인을 배관 구조와 내시경으로 점검합니다. 고압세척 필요 조건과 비용 결정 요인을 확인하고 상담을 접수하세요.
```

### 7.3 헤딩 구조

```text
H1 지역 + 메인 서비스
├─ H2 이런 증상이 있다면 점검이 필요합니다
├─ H2 주요 원인
│  └─ H3 원인별 설명
├─ H2 작업 과정
│  └─ H3 진단 / 작업 / 확인
├─ H2 비용이 달라지는 이유
├─ H2 서비스 가능 지역
├─ H2 자주 묻는 질문
└─ H2 관련 서비스와 인접 지역
```

H4를 주요 목차로 사용하는 경쟁 사이트의 구조는 따르지 않는다.

### 8.1 링크 그래프


## 10. 구조화 데이터 사양

페이지 유형에 따라 필요한 타입만 출력한다.

### 10.1 전 페이지 공통

- `WebPage`
- `BreadcrumbList`
- 사업체 정보가 정확할 경우 `PlumbingService` 또는 `LocalBusiness`

### 10.2 FAQ 포함 페이지

- 화면에 실제 표시된 질문과 답변만 `FAQPage`로 출력
- 숨긴 키워드용 질문 생성 금지

### 10.3 서비스 페이지

- `Service`
- `areaServed`는 실제 출동 범위만 포함

### 10.4 이미지 캐러셀

- 현행 프로젝트 원칙대로 독립 `ItemList` JSON-LD 블록 사용
- 페이지당 한 개
- 동일 출처 이미지 URL 사용
- 이미지마다 실제 장면을 나타내는 이름 제공

### 10.5 구조화 데이터 검증 규칙

- 전화번호, 주소, 운영시간은 화면과 JSON-LD가 일치해야 한다.
- 브랜드가 없는 페이지에서 임의 브랜드를 생성하지 않는다.
- 홈페이지를 근거 없이 `Article`로 선언하지 않는다.
- `dateModified`는 실제 콘텐츠 변경 시에만 갱신한다.

## 11. 전환 설계

경쟁 사이트는 전화 전환에 집중한다. 우리 시스템은 전화와 자체 DB폼을 함께 사용한다.

### 11.1 CTA 배치

```text
헤더 전화
→ 히어로 전화·접수
→ 작업 과정 뒤 상담
→ 비용 섹션 뒤 견적 접수
→ 페이지 하단 폼
→ 모바일 고정 전화
```

### 11.2 폼 필드

필수:

- 지역
- 문제 유형
- 연락처
- 개인정보 수집 동의

선택:

- 건물 유형
- 증상
- 희망 연락 시간
- 문의 내용

### 11.3 이벤트

| 이벤트명 | 발생 조건 |
|---|---|
| `page_view` | 페이지 로드 |
| `phone_click` | 전화 링크 선택 |
| `form_open` | 폼 노출/열기 |
| `form_submit` | 접수 성공 |
| `faq_open` | FAQ 펼침 |
| `related_click` | 관련 지역·서비스 이동 |

개인정보 및 연락처는 외부 분석 도구의 이벤트 값으로 전송하지 않는다.

## 13. 품질 검사와 빌드 게이트

### 13.1 페이지 단위 검사

- H1 정확히 1개
- title과 description 존재
- canonical이 자기 자신을 가리킴
- title 권장 길이 준수
- description 권장 길이 준수
- 지역명과 메인 키워드가 H1에 존재
- FAQ 화면 내용과 JSON-LD 일치
- 이미지 width/height/alt 존재
- 전화 링크 형식 정상
- 폼 action 및 group key 정상
- 깨진 내부링크 없음
- HTML 언어 `ko-KR`

### 13.2 중복·도어웨이 방지 검사

- 동일 호스트 내 title 완전 중복 0건
- description 완전 중복 0건
- 본문 정규화 해시 완전 중복 0건
- 인접 페이지 간 본문 유사도 기준 초과 시 실패 또는 보고
- 본문에서 대표 지역 이외의 지역명 과다 출현 시 경고
- 키워드 목록 형태가 일정 길이를 넘으면 실패
- 메인 키워드 반복 횟수 상한 적용
- 존재하지 않는 행정구역 조합 검출

권장 초기 기준:

```text
H1 개수: 1
본문 최소 길이: 1,200자
메인 키워드 정확 일치: 본문 3~8회
대표 지역명 정확 일치: 본문 3~8회
연속 키워드 나열: 5개 초과 금지
관련 내부링크: 4~8개
FAQ: 3~5개
```

이 수치는 절대 SEO 공식이 아니라 빌드 이상치를 잡기 위한 내부 기준이다.

### 13.3 샘플링 검사

배포 전에 다음 표본을 렌더링한다.

- 각 phase별 10페이지
- 수도권/광역시/시·군/읍·면 지역 각각 5페이지
- 비용·긴급·원인·방법·사례 의도 각각 5페이지
- 총 50페이지 이상 데스크톱·모바일 시각 검사

## 14. 구현 단계

### Phase 0 — 기준선 확보

- 현재 템플릿과 생성 페이지 샘플 100개 저장
- title, description, H1, 본문 해시, 내부링크 현황 리포트 생성
- 현재 빌드·배포 바이트 결정성 확인

완료 조건:

- 변경 전후를 비교할 기준 리포트가 존재한다.

### Phase 1 — 콘텐츠 데이터 모델

- 의도, 건물 유형, 증상, 원인, 작업 과정 데이터 풀 정의
- FAQ에 서비스·의도 태그 부여
- 지역 인접 관계 파생 파일 생성
- 기존 `siteIndex/pageId` 배정을 바꾸지 않는 선택 규칙 구현

완료 조건:

- 임의 페이지 ID를 입력하면 완전한 페이지 데이터 객체가 결정적으로 생성된다.

### Phase 2 — 템플릿 개편

- H1·breadcrumb·증상·원인·작업·비용·지역·FAQ·관련 링크 구성
- 모바일 고정 전화와 자체 접수 폼 유지
- 세 phase별 콘텐츠 블록 분기

완료 조건:

- 막힘·수전·누수 샘플이 서로 다른 정보구조와 문구를 갖는다.

### Phase 3 — SEO·구조화 데이터

- 페이지 타입별 JSON-LD 출력
- canonical, OG, title, description 규칙 적용
- sitemap과 실제 URL 일치 검증

완료 조건:

- 샘플 페이지 구조화 데이터 및 내부 링크 검사 통과.

### Phase 4 — 품질 게이트

- 중복 검사
- 키워드 과다 반복 검사
- 잘못된 지역 혼입 검사
- HTML, 링크, 이미지, 접근성 검사

완료 조건:

- 배포 스크립트가 품질 검사 실패 시 중단된다.

### Phase 5 — 제한 배포

- 한 호스트, 소량 페이지로 파일럿
- 사용자 행동과 크롤러 접근, 리드 이벤트 확인
- 기존 페이지와 비교 후 확대 여부 결정

주의: 실제 배포·수집요청·DB 변경은 운영자 확인 후 별도 실행한다.

## 15. 경쟁 사이트 대비 목표

| 항목 | 경쟁 사이트 | 우리 목표 |
|---|---|---|
| URL | 무작위 문자열 다수 | 현행 숫자 URL 유지, 논리 구조는 breadcrumb로 보완 |
| 지역 타기팅 | 구 페이지 + 동 키워드 대량 나열 | 대표 지역 페이지 + 사용자용 하위 지역 목록 |
| 콘텐츠 | 장문 사례형 | 의도·건물·증상 기반 장문 |
| 키워드 | 반복 강함 | 문맥 중심, 반복 상한 |
| 내부링크 | 대량 exact-match | 서비스·지역·가이드 균형 |
| H1 | 지역 페이지는 있음, 홈은 없음 | 전 페이지 정확히 1개 |
| FAQ | 화면+FAQPage | 동일, 내용 일치 검사 추가 |
| Local SEO | 넓은 areaServed | 실제 제공 범위만 선언 |
| 전환 | 전화 중심 | 전화 + 자체 DB폼 + 이벤트 |
| 품질 관리 | 오탈자·타 지역 혼입 | 자동 빌드 검사 |

## 16. 개발 완료 정의

다음 조건을 모두 만족해야 벤치마킹 적용 완료로 본다.

- 홈, 막힘, 수전, 누수 페이지의 정보구조가 명확히 구분된다.
- 모든 페이지에 H1이 정확히 하나 있다.
- 지역·키워드·의도가 데이터 모델에서 분리되어 있다.
- 지역명만 바꾼 동일 문서가 생성되지 않는다.
- 하위 행정구역이 키워드 도배가 아닌 서비스 범위로 표현된다.
- 서비스 페이지와 인접 지역 링크가 규칙적으로 연결된다.
- 화면 내용과 JSON-LD가 일치한다.
- 전화와 리드 폼이 정상 동작한다.
- 중복·지역 혼입·키워드 과다 검사가 빌드 과정에 포함된다.
- 50페이지 이상의 표본 시각·콘텐츠 검사를 통과한다.
- 기존 결정적 페이지 배정과 URL, 지역 풀을 깨지 않는다.

## 17. 구현 전 확정이 필요한 선택 사항

본 문서는 조사·기획까지만 수행했으며 아래 값은 임의로 변경하지 않았다.

1. 현재 `piping-v3` UI를 부분 개편할지, 지역 페이지 템플릿을 전면 교체할지
2. 400만 페이지 전체에 새 구조를 한 번에 적용할지, 신규 phase부터 적용할지
3. 비용 섹션에 실제 가격 범위를 제공할 수 있는지
4. 실제 출동 가능 지역과 운영시간의 최종 범위
5. 현장 사례를 실데이터로 공급할지, 일반 시나리오형 설명으로 제한할지
6. 페이지당 허용할 하위 동·읍·면 노출 개수
7. 기존 이미지의 타 업체 워터마크·전화번호 사용 여부
